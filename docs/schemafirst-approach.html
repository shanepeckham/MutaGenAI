Schema-First Agent Design

A methodology for building LLM-powered reasoning agents around a single, lightweight output schema that drives the entire lifecycle: prompt, tool use, evaluation, and human review.

This document explains the approach using a fictional example so you can apply it to your own domain.

1. The Core Idea

Most agent prompts mix four concerns into one giant instruction block:

  1. Role and tone
  2. Reasoning steps
  3. Output format
  4. Quality rules

Long, prose-heavy prompts are hard to evaluate, hard to review, and drift quickly as requirements change.

Schema-first flips this. You start by writing the schema of the final deliverable in JSON, Typescript, or any structured notation. The schema is the task definition. Everything else — prompt, tools, evaluator, UI — is derived from it.

2. A Fictional Walk-Through: "Incident Triage Reports"

Imagine a fictional reliability team that wants an agent to take a raw production incident description and produce a triage report. We'll use this throughout.

2.1 Step 1 — Define the schema

{
  "Executive Summary": str,
  "Incident Facts": {
    "Reported At": str,
    "Affected Service": str,
    "Symptoms": [str],
    "Blast Radius": str
  },
  "Service Classification": {
    "Tier": str,          # e.g. T0/T1/T2
    "Owning Team": str
  },
  "Probable Root Causes": [
    { "hypothesis": str,
      "supporting_signals": [str] }
  ],
  "Recommended Actions": [
    { "action": str,
      "owner": str,
      "urgency": str }
  ],
  "Citations": [
    { "source": str,
      "evidence": str }
  ],
  "Confidence Assessment": {
    "score": str,        # score of 0-100
    "key_assumptions": [str],
    "risk_drivers": [str]
  }
}

That's the entire "spec". Notice it carries intent via field names and inline comments — the model reads them as guidance.

2.2 Step 2 — Write a concise prompt

The prompt is short: a role, the schema, and a small set of rules.

You are an SRE assistant producing incident triage reports.

Produce a single JSON object matching this schema:
<schema>

Rules:
- Use the runbook search tool to ground every probable cause in real signals.
- Cite the lowest-level source available (dashboard panel, log query, runbook section).
- Rank monitoring evidence above anecdotal Slack reports.
- Do not speculate beyond cited signals.
- Output ONLY the JSON object.

The model decides how to use its tools. The schema tells it what must be true of the answer.

2.3 Step 3 — Derive the evaluation plan

For each leaf or sub-tree in the schema, pick a metric:

Schema field Metric type Why
Executive Summary LLM-as-judge (good/fair/bad) Subjective synthesis
Incident Facts.* Exact-match / extraction F1 Deterministic ground truth
Probable Root Causes[] Judge + grounding check Needs reasoning + citation check
Citations[] URL reachability + relevance score (1–5) Cheap, automatable
Confidence Assessment.score Calibration error vs. SME rating Numeric

The evaluator is itself a schema-first agent. Its output schema mirrors the producer's schema, with a {judgment, reason} block per field — for example:

{
  "Executive Summary": {
    "judgment": str,  # good|fair|bad
    "reason": str },
  "Incident Facts": {
    "judgment": str,
    "reason": str },
  "Probable Root Causes": { 
    "judgment": str,
    "reason": str },
  "Citations": [
    { "source": str,
    "relevance_score": int,  # score of 1-5
    "reason": str }
  ],
  "Confidence Assessment": {
    "judgment": str,
    "reason": str }
}

Because the eval schema is structurally aligned with the output schema, you can drill into which field regressed when a new prompt or model is rolled out — instead of staring at a single opaque score.

2.4 Step 4 — Auto-rendered SME review tool

The same schema becomes the layout for a human review UI. Each field gets a viewer, an inline editor, and a rating widget chosen by field type:

  • Long-form narrative fields → 👍 / 👎
  • Structured / list fields → Good / Fair / Bad
  • Citations → per-item relevance score

A reference implementation is one example. A minimal SME feedback record — regardless of UI choice — looks like:

{
  "entry_id": "incident-0427",
  "field": "Probable Root Causes",
  "rating": "fair",
  "edited_value": [ /* SME-corrected list */ ],
  "note": "Missed the upstream DNS flap as a candidate cause."
}

3. Why this approach pays off

Benefit How the schema enables it
Shorter, more stable prompts Field names + comments replace paragraphs of instructions.
Targeted evaluation Each field is independently scorable; regressions are localized.
Fast prototyping of review UIs The schema is the form definition.
Tool-agnostic agent The model picks tools to satisfy the schema — swap Bing for an internal KB without touching the prompt.
Better SME feedback loops SMEs rate small, focused chunks rather than walls of text.
Cleaner training data Edited outputs are already structured — directly usable for SFT or DPO.
Versionable contract Schema diffs are reviewable in PRs; prompt/eval/UI changes follow automatically.

4. Applying the approach to a new task

  1. Sketch the deliverable as JSON. Use field names and # comments or // comments to encode intent. Keep it flat where possible; nest only where a sub-structure is genuinely reused.
  2. Write a ≤ 1-page prompt. Role, the schema, a handful of hard rules, and tool-use guidance. Resist the urge to enumerate edge cases — push those into the schema.
  3. Mirror the schema into an evaluator schema. For each field, pick the cheapest metric that catches the failure modes you care about.
  4. Generate a review form from the schema. Pick a rating widget per field type and persist edits + ratings alongside the outputs.
  5. Iterate on the schema, not the prose. When SMEs flag a gap, ask: "what missing field or refined constraint would have prevented this?" — then update schema, prompt, evaluator, and UI together.

5. Getting started

  1. Draft the schema. Capture the deliverable as a structured object with intent-bearing field names.
  2. Author the prompt. Embed the schema, add the role and a short list of rules, and grant the agent the tools it needs to ground its answers.
  3. Run the agent on a representative set of inputs and persist outputs in a structured, line-delimited format.
  4. Author the evaluator by mirroring the schema and attaching a metric to each field; run it over the same outputs to get per-field scores.
  5. Render a review UI from the schema and have SMEs rate and edit each field; persist their feedback alongside the outputs.
  6. Triage the gaps. Combine evaluator scores and SME feedback to find the weakest fields, refine the schema (and downstream artifacts), and iterate.
